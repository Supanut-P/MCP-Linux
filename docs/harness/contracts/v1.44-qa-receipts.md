# v1.44 source-bound QA receipts and bounded retry

Prerequisite: v1.43 verification is closed, including its Ubuntu closure receipt.
Keep metadata 1.43.0 until implementation QA. Preserve primary dirty work.

Extend caller-native durable workflow coordination; do not add an executor.
The server may validate immutable receipt fields, source state and artifact
integrity, but it does not run task commands, dispatch or resume workers, or
prove that a caller-reported person or process performed the stated work.

Create a server-generated immutable receipt for each verification attempt. Bind
it to the workflow/task/attempt IDs, lease ID and fencing revision, immutable
contract SHA-256, claim baseline fingerprint, current source fingerprint,
diff fingerprint, verification revision, verdict (`passed`, `failed`, or
`blocked`), summary, verification bounds, criterion results, and command
evidence. A start request may omit `workerId` to preserve invocation
compatibility. When supplied, worker identity remains caller-attested; it is
not authenticated by the server. The review submission is limited to 16 KiB.

Allow at most 16 command results, one per referenced contract command index,
with caller-reported exit code and exactly one artifact record per result.
For a passing verdict, require every command and every one of the contract's
up to 32 acceptance criteria, each with a passing result; command exit codes
must match the contract. Failed or blocked verdicts may include partial
evidence. Artifact paths are relative to and resolved through the registered
workspace guard. Verify stable regular-file size and SHA-256, at most 2 MiB per
artifact and 8 MiB total. Reject escapes, symlinks, hardlinks, special files,
truncation, unstable reads, changed hashes, duplicate or invalid indexes, and
oversized submissions. Never persist raw command output or credentials in
workflow metadata. Artifact hashes establish integrity of the bytes read, not
that a command produced them or that an artifact is truthful.

The review operation must carry `sourceFingerprint` and `diffFingerprint` as
explicit caller-bound fields. The server recaptures source, validates the
handoff against the claim baseline and contract scope, and rejects either value
unless it matches the server-checked verification. It then freezes the accepted
or rejected submission into a new server-generated immutable receipt. At review
and done, recheck source freshness and artifact hashes against that receipt; a
moved, missing, or changed artifact invalidates it. This checks the caller's
binding to the exact verified handoff without claiming that the caller ran the
commands.

Use additive migration 013. Store receipts append-only; database guards reject
receipt update/delete and reject writes to every workflow table from a v1.43
connection. Preserve read compatibility for old binaries. A legacy `done` task
without a v1.44 accepted receipt remains `done` with `verification=legacy_unverified`;
do not synthesize a receipt or silently re-run it. A v1.43 binary must not
change workflow, task, event, lease, reservation, attempt, verification, or
receipt state after migration.

Add explicit `review` and `retry` operations. A review binds an attestation and
verdict to the exact immutable receipt, task revision, and source/diff
fingerprints. Require the attested reviewer identity to differ from every
available worker identity across all attempts for that task, not only the latest
worker. If a start omitted `workerId`, the reviewer must attest independence
from that worker too; server checks can only compare identities that were
supplied. Store only bounded, privacy-preserving identity keys where possible.
The caller attests that the reviewer independently inspected the patch, source,
command evidence, and artifacts. Identity, execution, and review activity remain
caller-reported; server-checked integrity means the server validated identity
separation as supplied, ownership/policy, immutable bindings, source freshness,
and artifact hashes. It is not identity authentication or proof of independent
human judgment.

A passing review appends an accepted receipt and leaves the task `verifying`.
The normal `done` transition must then recheck owner, current write permission,
claim/lease fencing, task and verification revisions, and an exact fresh match
for the accepted receipt's current source and diff fingerprints. A source or
revision change invalidates the receipt for completion and requires new
verification and review. Never let a failed, blocked, stale, or caller-only QA
report authorize `done`.

Permit at most three attempts per task: attempt 1 requests Luna, attempt 2
requests Luna, and attempt 3 requests Sol. These are caller-native model
requests, not proof of the model selected or provider availability. A failed
review moves the task to `failed` and quarantines its lease and reservations.
Retry is allowed only from `failed`, after explicit owner reconciliation
confirms that the previous native writer stopped and reviews its effects, and
the prior scope has been explicitly released under current WRITE permission.
Invalidate the old claim/fence before allocating the next attempt and fresh
lease. Do not auto-release quarantine or auto-admit a replacement writer.
`blocked`, `done`, and `cancelled` tasks cannot retry. Attempt four is always
rejected. A reviewer `blocked` verdict leaves the task blocked and quarantines
its scope; it is not a failed attempt eligible for retry. Cancellation never
dispatches cleanup or resumes work.

Active v1.43 tasks have no attempt identity and cannot be upgraded by
manufacturing an attempt or receipt. Stop caller-native work, reconcile its
state and effects under the existing owner gate, then replan it as a v1.44 task
before starting a new attempt. A legacy `done` task remains unverified as
described above.

Store attempt, receipt, review, task transition, fencing changes, and ordered
event atomically. Enforce owner, workflow, task, attempt, lease, revision, and
receipt bindings at repository boundaries, not only in tool validation. A
receipt cannot be replaced or accepted under a later attempt. Keep cross-owner
conflicts opaque. Existing resume/status operations remain inspection-only and
must never dispatch or replay execution.

Acceptance: on real SQLite, reopen after receipt creation and review; immutable
receipt bytes and fingerprints remain stable. Exact command indexes, expected
and actual exits, attempt/lease/contract/baseline/current-source/diff/revision
bindings survive reopen. A successful review leaves `verifying`; `done`
requires the accepted receipt and a fresh identical source/diff/revision check.
Two workers cannot obtain a replacement lease while failed scope is quarantined.
After explicit reconciliation and release, retry increments the attempt and
uses a new fence. Verify prescribed Luna/Luna/Sol attempts and reject attempt
four. Prove old v1.43 writes fail against every guarded workflow table while
read-only legacy status remains available.

Negative tests must reject same reviewer/worker identity across any attempt;
wrong task, attempt, lease, contract hash, baseline, source, diff, or revision;
stale source after review; duplicate/missing/extra command indexes; exit-code
mismatches; missing, outside-root, symlinked, hardlinked,
unstable, truncated, oversized, or hash-mismatched artifacts; mutation/deletion
of receipts; stale tokens; cross-owner access; retries from `blocked`, `done`,
or `cancelled`; retry before reconciliation/release; automatic quarantine
release; and legacy `done` being treated as verified. Inject aborts and failures
around each transaction boundary and prove no partial receipt, review, attempt,
event, or state transition is visible.

Use independent processes for SQLite contention and run full Ubuntu, package,
installed STDIO/HTTP upgrade/rollback/recovery, old-binary compatibility, and
independent QA before v1.45. Report local checks, Ubuntu/package verification,
native provider readiness, and human approval separately. Receipts cannot prove
that caller-native commands actually ran, that the claimed model was used, that
worker processes stopped, or that writes stayed physically inside the
registered root. Workspace path/hash checks have an after-final-check TOCTOU
boundary; they are coordination and evidence controls, not an OS sandbox.

The immutable receipt records both the handoff `verificationRevision` and the
post-review `reviewRevision`. Completion requires that exact review fence.
Reverification preserves historical receipts, invalidates the current accepted
receipt, and requires a fresh review; historical evidence is never overwritten.
Stored receipt metadata, including server-derived contract command fields, is
bounded to 64 KiB per receipt (submission remains 16 KiB).

Terminal inspection clarification after bounded implementation review: accepted
completion evidence is associated with the exact recorded `done` event at
`reviewRevision + 1`, not subsequent reconciliation revisions. Reconciliation
releases coordination scope and must not erase the completed receipt association.
A completed receipt is historical evidence of that source/diff, not a fresh
claim about current filesystem contents. Verify done/reconcile/reopen explicitly.

# v1.46 fleet groups and service-to-workspace mapping

v1.45 Ubuntu verification is closed. This milestone adds bounded local metadata
for selecting registered targets. It never executes SSH, reads workspace files,
dispatches models, or expands an existing registration's permissions.

Add `fleet_catalog` with `put_group`, `put_mapping`, `list`, `resolve`, `remove`.
A group binds 1–20 distinct host IDs. A mapping binds one registered host,
validated systemd service unit and registered workspace. No hostname, credential,
command, arbitrary path or caller owner key is accepted. Existing `remote_fleet`
request shapes remain unchanged; callers explicitly pass resolved IDs to it.

Ownership follows existing workflow conventions: SHA-256 of the server-provided
actor client ID. It isolates catalog metadata, not the global host/workspace
registries or physical hosts. READ applies to listing/resolution; mutations
require current WRITE permission and explicit confirmation if policy requests it.
Mutations use optimistic revisions (0 creates; existing revision updates/removes)
and bounded audit summaries. No saved approval grants subsequent execution.

Snapshot canonical hashes of host connection/security fields, ordered roots and
registration time, plus workspace registered root/identity. Resolve rechecks
registrations: missing is `unavailable`; a changed hash is `stale`. Both withhold
usable target references. Partial group results remain explicit and bounded.
Explicit update can rebind with the current revision. Hashes establish bytes,
not current remote physical identity. Content-identical re-registration with a
reused timestamp cannot establish a new incarnation.

Use one additive SQLite table, owner/ID composite key, bounded validated JSON,
revision, timestamps and per-owner/global quotas: 32 groups, 128 mappings per
owner; 1,024 total entries. Transactionally enforce limits and revision changes.
Do not add triggers to host/workspace tables or change existing migrations.
Older binaries ignore catalog metadata; later resolution detects changed
registrations. Startup follows existing transactional migration backup policy.

Verification: negative parser, owner spoof/cross-owner, READ/WRITE confirmation,
quotas/corrupt state, duplicate IDs, mixed resolved/stale/unavailable members,
host/workspace rebinding/removal, revision races and restart persistence. Preserve
v1 fleet behavior. Full local and Ubuntu/package gates, installed STDIO/HTTP
catalog checks, package lifecycle and native connector checks must pass before
v1.47 starts. Source-bound receipts distinguish fixtures from live remote reads.

One worker writes storage only; Lead writes application/tool wiring; independent
Sol reviews integration. No overlapping writer scopes, new dependencies, global
configuration, credentials, publication or production actions.

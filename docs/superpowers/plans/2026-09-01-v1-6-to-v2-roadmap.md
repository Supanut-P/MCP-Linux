# Baitonghub-Linux-mcp v1.6 to v2 Decision Roadmap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the v1.5 Linux-headless runtime into a discoverable, durable, safely operated MCP server without widening filesystem, process, credential, database, or remote-host authority.

**Architecture:** Keep v1 releases additive and reuse the existing registered-workspace, registered-target, Secret Service, permission, audit, durable-task, and fixed-operation remote-host boundaries. Add one narrowly scoped product capability per minor release, require an Ubuntu 24.04 packaged-runtime proof for every release, and open a v2 contract only when collected compatibility evidence proves that a breaking change is necessary.

**Tech Stack:** TypeScript, Node.js 24, MCP TypeScript SDK, Zod, SQLite `DatabaseSync`, OpenSSH, systemd, pnpm 10.15.0, Vitest, Ubuntu 24.04 x64.

---

## Current baseline and non-negotiable boundaries

- Source version is `1.5.0` at local commit `8b3e547`; it has not been pushed, tagged, or released.
- The seven-day soak is explicitly waived. The release must carry `docs/linux/evidence/v1.5.0/SEVEN_DAY_SOAK_WAIVER.md` and must not claim production-soak evidence.
- The current runtime exposes 210 tools. New functionality should extend an existing tool when the permission class remains truthful; otherwise add at most one new public tool per minor release.
- Target metadata is registered locally. Secret values remain in Linux Secret Service or an explicitly supplied headless environment variable and never enter MCP input, CLI argv, logs, audit records, support bundles, or release artifacts.
- Filesystem access remains inside canonical registered roots. Remote access remains limited to registered host IDs, pinned fingerprints, and registered remote roots.
- Dangerous work keeps dry-run or plan output, a hash bound to the exact request, explicit confirmation, an expiry, bounded concurrency, cancellation, and sanitized audit evidence.
- `sudo`, root escalation, shutdown, format, mount, workspace-root deletion, unowned process termination, arbitrary remote shell, and plaintext secret fallback remain hard-blocked.
- Existing `v2.0.0`, `v2.1.0`, and `v2.2.2` tags collide with inherited historical tags. No tag is deleted or replaced as part of this plan. A future v2 release needs an explicit tag-namespace decision and human approval.

## Release sequence

| Version | Product outcome | Public contract change | Release gate |
| --- | --- | --- | --- |
| v1.5.0 | Close the operational release without a seven-day claim | No new tool | Ubuntu package/install/upgrade/rollback proof |
| v1.6.0 | Let an MCP client discover safe target aliases and let the local operator manage target lifecycle | Add read-only `target_catalog`; add CLI lifecycle commands | No host address, username, fingerprint, root path, or secret reference in MCP results |
| v1.7.0 | Create and follow durable shell work through standard MCP Tasks | Add task support metadata and task-augmented `tools/call` for `shell` only | Restart/reconnect/owner/cancel proof through packaged HTTP MCP |
| v1.8.0 | Roll out a service restart across registered hosts with a canary and bounded batches | Add dangerous `remote_rollout` | Aggregate preview hash, expiry, explicit confirmation, per-host audit, stop-on-canary-failure |
| v1.9.0 | Produce a sanitized support artifact and durable approval evidence | Add write-scoped `support_bundle`; additive audit metadata | Secret-canary scan and deterministic bundle manifest |
| v2.0.0 decision | Break the contract only if v1 evidence proves it is required | Separate v2 contract and migration guide | Usage evidence, dual-contract tests, tag decision, explicit human approval |

const remoteRolloutSchema = z.discriminatedUnion('operation', [

## v2.0 decision gate

Do not change the package to `2.0.0` until all of these are true:

- [ ] At least one real client incompatibility cannot be solved by an additive v1 field, optional capability, or profile.
- [ ] `tests/fixtures/tool-contract-v1.json` remains frozen and a new `tests/fixtures/tool-contract-v2.json` is generated separately.
- [ ] `docs/migrations/V1_TO_V2.md` maps every removed, renamed, or behavior-changing tool and includes rollback instructions.
- [ ] Packaged acceptance runs the same scenario against a v1 compatibility profile and the v2 default profile.
- [ ] The release tag collision is resolved by explicit approval: either remove/replace the inherited historical `v2.*` tags or adopt and document a Baitonghub-specific tag namespace while keeping package version `2.0.0`.
- [ ] The user explicitly approves implementation of the breaking contract and separately approves the eventual tag/release operation.

The preferred v2 candidate, if usage evidence supports it, is a smaller truthful `tools/list` surface selected by explicit server profile (`core`, `operator`, or `fleet`) while preserving the v1 compatibility profile. It must not widen authority, infer credentials, auto-register `/`, or translate an unavailable operation into false success.

# Baitonghub-Linux-mcp v1.12–v2.0 Additive Development Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Continue Baitonghub-Linux-mcp from the locally verified v1.11.0 headless release to a more useful Linux operations gateway through bounded, additive features, while keeping v1 compatibility and the existing registered-root, ownership, confirmation, audit, and secret-redaction boundaries.

**Architecture:** Ship one independently testable capability per minor release. Reuse the existing `LinuxCommandRunner`, `LinuxObservabilityBackend`, `WorkspaceIndexService`, `RemoteFleetBackend`, `ActivityTracker`, durable task stores, and generated tool-contract checks. The default server remains Linux headless and v1-compatible; no release in this plan grants arbitrary root filesystem access, arbitrary remote shell, plaintext secrets, or unowned process control.

**Tech Stack:** TypeScript, Node.js 24, MCP SDK `2026-07-28`, Zod, SQLite, systemd/journalctl, procfs, OpenSSH, pnpm 10.15.0, Vitest, Ubuntu 24.04 x64, DEB and Linux x64 tar packaging.

- The seven-day soak is explicitly waived. Every release note must say that it has not run and must not claim production-soak evidence.
- The stale exact-order expectation in `packages/mcp-server/src/tool-registry.test.ts` was corrected as part of this checkpoint; `remote_fleet`, `service_logs`, and generated catalog/contract files are synchronized.
- Every minor release follows the same loop: write a failing test, implement the smallest bounded provider, run focused tests, run the full Ubuntu gate and packaged smoke, update docs/version/provenance, then stop at the human gate before external push/tag/release.

## Release map

| Version | User value | Public change | Hard acceptance gate |
| --- | --- | --- | --- |
| v1.12.0 | Follow one systemd service log stream without shell commands | Add read-only `service_logs` with fixed unit validation, byte/line caps, and opaque cursor | Cursor cannot escape its unit, output is capped/sanitized, and missing journalctl returns structured unavailable |
| v1.13.0 | See whether the gateway or host is overloaded | Add read-only `runtime_metrics` snapshot for host, MCP runtime, and owned tasks | No command-line/env/secret disclosure; deterministic bounded JSON and truthful missing-provider state |
| v1.14.0 | Detect workspace changes between agent turns | Add read-only `workspace_changes` snapshot/diff over the existing index/watch queue | Only registered workspace paths, bounded event retention, opaque cursor owner-isolated, no file contents returned |
| v1.15.0 | Check many registered hosts in one operation | Extend `remote_fleet` with bounded `snapshot` and per-host progress, without new remote authority | 1–20 registered hosts, max four sessions, per-host sanitized errors, deterministic partial result |
| v1.16.0 | Run the same server as a small core, operator, or fleet surface | Add opt-in additive server profiles; default remains v1-compatible full headless profile | `tools/list` filtering is explicit, stable, and cannot elevate permissions or reveal secret metadata |
| v2.0.0 decision | Only address a proven incompatibility | Separate v2 contract only when real client/deprecation evidence requires breaking change | Frozen v1 fixture, new v2 fixture, migration/rollback proof, and explicit approval |

## v2.0.0 decision gate

After v1.16, collect actual `tools/list` and error telemetry from the audit-safe aggregate (counts and result codes only). Do not start v2 implementation unless all conditions hold:

- [ ] A real client incompatibility cannot be solved by an optional field, additive tool, or profile.
- [ ] `tests/fixtures/tool-contract-v1.json` remains frozen and `tests/fixtures/tool-contract-v2.json` is generated separately.
- [ ] `docs/migrations/V1_TO_V2.md` maps every removed/renamed/behavior-changing field and includes rollback.
- [ ] Packaged acceptance runs the same scenario against the v1 compatibility profile and the proposed v2 default.
- [ ] Any historical tag collision has an explicit namespace decision.
- [ ] The user separately approves implementation and later push/tag/release mutations.

If the evidence does not satisfy every item, continue additive v1 maintenance and security fixes; do not manufacture a v2 breaking change merely to increase the version number.
